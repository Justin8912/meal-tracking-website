Nourish — meal-tracking-website

Personal meal planning and nutrition tracking application. Provides a recipe library, a 7-day weekly planner with drag-and-drop scheduling, and full macro/micronutrient computation backed by the USDA FoodData Central database.

Node.js ≥20 Fastify 5.8 React 18.3 PostgreSQL 16 TypeScript 5.7 Drizzle ORM TanStack Query 5 Docker Compose npm workspaces monorepo

What it does

Primary Resource

Recipe library with ingredient composition. Each recipe carries a complete macro/micronutrient profile derived from USDA-sourced or custom ingredients, computed by the shared nutrition-engine package.

Source of Truth

PostgreSQL is the system of record for all user data. USDA FoodData Central is the authoritative source for food nutrition data; fetched payloads are cached locally in usdaFoodCache.

Downstream Effects

The weekly planner draws from the recipe library to produce per-day and weekly macro summaries. Freeform meal entries are supported but excluded from aggregated nutrition totals.

External Dependencies

This is a personal project running on Docker Compose — there are no AWS resources, no cloud observability services, and no identity providers. The only external runtime dependency is the USDA nutrition database API.
ServiceBase URLAuthPurposeFailure Mode
USDA FoodData Central https://api.nal.usda.gov/fdc/v1 API key via USDA_API_KEY env var (optional) Food search and nutrition detail. Used by GET /ingredients/search and GET /ingredients/usda/:fdcId. Graceful degradation — ingredient search returns an error envelope; items already cached in PostgreSQL remain available; custom ingredients are unaffected.
No USDA key configured: The key is optional but recommended for production use. Without it, USDA requests will be unauthenticated and may be rate-limited. Set USDA_API_KEY in .env.

DELETE /api/v1/plans/:id Hard-delete plan entry PostgreSQL — planEntries (write) 204 or 404.

GET /api/v1/plans/daily-summary Per-day macro breakdown PostgreSQL — same as summary Query: weekStart. Returns 0–7 day objects: {dayOfWeek, hasData, calories, proteinG, carbsG, fatG, fiberG}.

Authorization

Single-workspace, single-user design. There is no JWT, session, or API-key authentication. All requests operate against workspace ID 00000000-0000-0000-0000-000000000001 (seeded by migration 0001, resolved by workspace.ts). This is appropriate for a self-hosted personal application — enforce access at the network layer.

Shared Libraries

Two npm workspace packages consumed by both the API and Web components. They are not deployable units — they ship as source into each app's build.

@meal-tracking/shared

The shared type contract between API and Web. Zod schemas are used by Fastify route handlers for request body validation; TypeScript types are inferred from the same schemas, guaranteeing consistency across the boundary.

ExportKindDescription
MealType, MealSlotType + Schema'breakfast' | 'lunch' | 'dinner' | 'snack'
Nutrition, MicronutrientType + SchemaMacro fields plus a Record<string, Micronutrient> map. Micros stored as absolute mass (mg/mcg), never %DV.
Ingredient, Recipe, RecipeDetailType + SchemaCore recipe library domain objects
RecipeInputType + SchemaWrite payload for creating/updating recipes; includes ingredient lines and tag labels
PlanEntry, PlanEntryInputType + SchemaPlanner types. PlanEntryInput enforces the recipeId XOR freeformTitle constraint via Zod discriminated union.
WeeklySummaryType + SchemaWeekly macro totals with countedEntryIds and excludedEntryIds lists
ErrorEnvelopeType + SchemaUniversal API error shape: { error: { code, message } }

@meal-tracking/nutrition-engine

A pure computation library with zero runtime dependencies. No I/O, no Date, no side effects. Implements all nutrition math: unit-to-gram resolution, per-ingredient macro scaling, full-precision accumulation, and display rounding.

ExportDescription
toGrams(quantity, unitCode, ingredient)Resolves a usage quantity to grams using the ingredient's gramEquivalents density map and gramWeightPerQty. Returns { resolved: true, grams } or { resolved: false, reason }.
computeRecipeNutrition(lines, servings)Full-precision accumulation across all ingredient lines. Returns { total, perServing, completeness }. Absent macros are never zero-filled; they are flagged in completeness.missing.
formatNutrition(nutrition)Single rounding boundary for display. Returns FormattedNutrition (a distinct type to prevent re-summing already-rounded values).
Precision invariant: No rounding occurs until formatNutrition is called. All intermediate accumulation uses full floating-point precision to prevent compounding rounding error across multiple ingredients. This is why FormattedNutrition is a separate type from Nutrition.

How to Use

Testing is done on the server rather than locally. This gives access to the existing ingredients and recipes and avoids CORS issues that appear in a local dev environment.

Testing a branch on the server

  1. Tear down the running production containers: 
    sudo docker compose down
    Run this in home-server/apps/meal-tracking-website.
  2. Navigate to the test repo and check out the branch to test: 
    cd ~/test/meal-tracking-website
git checkout <branch-name>
  3. Build and start the containers: 
    sudo docker compose up --build

Run tests and lint

npm run test      # vitest across all workspaces
npm run lint      # tsc --noEmit + ESLint across all workspaces

Monitoring

This is a self-hosted personal project. There is no cloud monitoring (New Relic, PagerDuty, CloudWatch, Grafana). Observability is through structured JSON logs (Pino) and the built-in health endpoint.

Structured Logging (Pino)

All API logs emit as JSON to stdout. The following values are automatically redacted before any log line is written:

Redacted KeyReason
DATABASE_URLContains DB credentials
USDA_API_KEYThird-party API credential

Control log verbosity with the LOG_LEVEL environment variable. Stream logs in real time:

docker compose logs api -f   # API structured JSON logs
docker compose logs web -f   # Nginx access logs

PostgreSQL Health Check (Docker Compose)

The postgres service is configured with a pg_isready health check. The api service has depends_on: postgres: condition: service_healthy — the API never starts before the database is accepting connections.
